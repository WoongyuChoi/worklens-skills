# 2차 추가 스킬 10개 — 설계와 출처

원문 확인 및 구현일: 2026-09-28. 상태: **10개 구현 완료 / 사내 반영 대기 / 사내 Qwen 미검증**.

기존 10개의 실무 적용 가능 평가가 6개였다는 피드백을 반영했습니다.
이번에는 한 번의 요청으로 쓸 수 있는 파일, 비교표, 수정본이 남는 후보를 골랐습니다.
아래 이름의 SKILL.md를 모두 구현했습니다. 설치 목록은 [README](../README.md), 구현 검증은 [VALIDATION](VALIDATION.md)에 있습니다.
아래 상세 내용은 발굴 당시의 설계 근거를 보존한 것입니다. 현재 정확한 지원 형식과 한도는 각 스킬의 SKILL.md와 references 문서가 기준입니다.

## 한눈에 보기

우선순위는 현재 알려진 사내 환경을 바탕으로 한 판단이며, 생산성 측정 결과가 아닙니다.

| 순서 | 후보 | 짧은 요청 | 바로 받는 결과 | 우선순위 |
|---|---|---|---|---|
| 1 | 데이터 대조 `data-reconcile` | 이 두 파일 안 맞는 것만 찾아줘 | 누락, 중복 키, 값 불일치 목록과 건수 | 우선 |
| 2 | 테스트 데이터 세트 `fixture-factory` | 이 입력 테스트할 데이터 만들어줘 | 정상/경계/오류 JSON·CSV와 예상 결과 | 우선 |
| 3 | 기존 화면 다듬기 `ui-polish` | 이 화면 좀 덜 답답하게 다듬어줘 | 기존 스타일에 맞춘 화면 코드 수정본 | 우선 |
| 4 | 업무 조건표 `rule-matrix` | 이 로직 조건별로 표로 뽑아줘 | 조건, 처리 결과, 예외, 코드 근거 표 | 우선 |
| 5 | 환경설정 대조 `config-compare` | 개발이랑 운영 설정 다른 것만 보여줘 | 누락 키, 값 차이, 미해결 변수 표 | 우선 |
| 6 | 문서와 구현 대조 `doc-drift` | 이 설명서 지금 코드랑 맞아? | 불일치 근거와 교체할 문장 | 우선 |
| 7 | 숫자 변동 분해 `variance-bridge` | 이번 숫자 왜 달라졌는지 풀어줘 | 전체 증감에 대한 항목별 기여도 표 | 상황별 |
| 8 | 현업 확인표 `acceptance-kit` | 현업한테 확인받을 표 만들어줘 | 조작 순서, 기대 결과, 판정 칸이 있는 검수표 | 상황별 |
| 9 | 조건 조합 압축 `pairwise-cases` | 조합이 너무 많으니 줄여줘 | 유효한 조건 쌍을 덮는 시험 조합과 커버리지 | 상황별 |
| 10 | 로그와 샘플 가명처리 `sample-mask` | 이 자료 식별정보 가려서 공유본 만들어줘 | 같은 값을 같은 토큰으로 바꾼 사본과 처리 내역 | 상황별 |

입력은 현재 대화와 명시한 파일, 현재 프로젝트에서 찾아 씁니다.
대상이 없거나 둘 이상이면 선택 질문 한 번으로 범위를 정합니다.
CLI 결론과 작은 표를 기본으로 하고, 많은 행의 탐색이나 화면 확인에 도움이 될 때 HTML을 씁니다.

## 1. 데이터 대조

- **쓸 장면:** 배치 전후 산출물, 서로 다른 시스템에서 내려받은 조회 결과, 이관 전후 CSV를 비교합니다.
- **스킬의 추가 가치:** 줄 순서 대신 업무 키로 맞추고, 추가/누락/중복/필드 차이를 일정한 규칙으로 분류합니다. 중복 키를 임의로 하나로 합치지 않습니다.
- **입력 부담:** 두 파일이 있으면 키 후보의 유일성을 검사합니다. 키가 불명확하면 후보만 짧게 제시합니다.
- **출력:** CLI 요약 + `reconciliation.csv`. 긴 숫자, 앞자리 0, null과 빈 문자열을 보존합니다.
- **기존과 차이:** file-explorer의 단일 파일 열람과 달리 두 집합의 정합성을 대조합니다.
- **원문:** GitHub 조직의 커뮤니티 모음 [sql-server-table-reconciliation](https://github.com/github/awesome-copilot/blob/main/skills/sql-server-table-reconciliation/SKILL.md).
- **반입 시 수정:** 원본의 SQL Server 연결, Python, Arrow 의존성을 제거하고 내보낸 CSV/JSON으로 범위를 제한해야 합니다. XLSX를 무조건 읽는다고 가정하지 않습니다. 큰 파일은 실행 가능한 로컬 처리기가 없으면 전체 대조 완료로 표시하지 않습니다.
- **선정 확인:** 순서가 다른 두 파일에서 같은 결과가 나오고, 중복 키와 숫자 정밀도 손실을 놓치지 않아야 합니다.

## 2. 테스트 데이터 세트

- **쓸 장면:** VO/DTO, 입력 검증 코드, 스키마를 바탕으로 바로 붙여 넣을 요청 데이터를 만듭니다.
- **스킬의 추가 가치:** 정상 한 건만 만드는 대신 길이 경계, 필수값 누락, 날짜 경계, 잘못된 코드 등을 규칙과 연결한 고정 세트로 제공합니다.
- **입력 부담:** 현재 대상 파일에서 제약을 읽습니다. 파일에 없는 업무 규칙은 확정하지 않습니다.
- **출력:** `valid.json`, `invalid.json`, `cases.csv`. 데이터와 예상 거부 사유를 함께 제공합니다.
- **기존과 차이:** qa-sweep은 변경된 결과를 검증하고, 이 후보는 검증에 넣을 실제 입력물을 만듭니다. 대량 조합 최적화는 9번 범위입니다.
- **원문:** Nao의 [test-data-generation](https://github.com/naodeng/awesome-qa-skills/tree/main/skills/en/testing-types/test-data-generation), 특히 [실행 지침](https://github.com/naodeng/awesome-qa-skills/blob/main/skills/en/testing-types/test-data-generation/prompts/test-data-generation.md).
- **반입 시 수정:** 원본의 긴 입력/출력 항목을 줄이고 소스에서 제약을 먼저 추출합니다. 소량의 재현 가능한 가상 데이터부터 제공합니다. Faker나 DB 삽입은 필수가 아닙니다.
- **선정 확인:** 같은 기준에서 재생성한 결과를 대조할 수 있고, 각 오류 케이스가 의도한 조건을 실제로 위반해야 합니다.

## 3. 기존 화면 다듬기

- **쓸 장면:** 화면은 만들어졌지만 글씨, 여백, 버튼 배치, 표의 밀도가 어수선할 때 사용합니다.
- **스킬의 추가 가치:** 현재 프로젝트의 화면 규칙을 찾아 정보 위계, 정렬, 빈 상태, 오류 문구를 일관되게 다듬습니다. 전체 재설계로 범위를 키우지 않습니다.
- **입력 부담:** 화면 경로 또는 현재 작업 맥락으로 시작합니다. 스크린샷이 있으면 함께 활용합니다.
- **출력:** 기존 소스 수정본과 주요 변경점 3개. 화면을 실제 열어봤을 때만 렌더링 확인으로 표시합니다.
- **기존과 차이:** screen-prototype은 새 예시 화면을 만들고, 이 후보는 이미 쓰는 화면을 다듬습니다.
- **원문:** Paul Bakaus의 [Impeccable](https://github.com/pbakaus/impeccable), [polish](https://github.com/pbakaus/impeccable/blob/main/.agents/skills/impeccable/reference/polish.md).
- **반입 시 수정:** 현 버전 원본은 실행 바이너리와 브라우저 연계 기능을 포함합니다. 이를 그대로 사용할 수 있다고 가정하지 않고, 화면 개선 절차를 분리해 한국어 가독성과 로컬 폰트에 맞춥니다. 바이너리 자동 다운로드는 제외합니다.
- **선정 확인:** 기존 공통 컴포넌트와 주요 동작을 유지하고, 대표 화면에서 수정 전후 가독성을 직접 비교해야 합니다.

## 4. 업무 조건표

- **쓸 장면:** 깊은 if/switch나 SQL CASE 안의 처리 조건을 현업 또는 동료에게 설명합니다.
- **스킬의 추가 가치:** 실행 순서와 우선 적용 규칙을 보존해 조건 → 결과 → 예외 → 근거를 표로 고정합니다. 알려진 입력을 대입한 예를 덧붙일 수 있습니다.
- **입력 부담:** 메서드나 쿼리 하나를 대상으로 시작합니다. 코드만으로 알 수 없는 업무 의미는 미확인으로 둡니다.
- **출력:** `rules.md`. 동일한 메타 필드명도 선언 타입, 모듈, 호출 위치가 다르면 별개로 다룹니다.
- **기존과 차이:** diagram-maker의 흐름도나 변경 영향 분석과 달리, 어떤 조건에서 어떤 결과가 나오는지를 정리합니다.
- **원문:** Forge의 [business-rule-extraction](https://github.com/pan94u/forge/blob/main/plugins/forge-foundation/skills/business-rule-extraction/SKILL.md). 커뮤니티 사례이며 독립 검증된 표준은 아닙니다.
- **반입 시 수정:** 원문의 전체 서비스 스캔과 일괄 완료 조건을 가져오지 않습니다. 사내 시스템은 SQL/XML에도 규칙이 있으므로 Service만 보고 끝내지 않습니다. 코드의 현재 동작과 승인된 업무 정책을 구분합니다.
- **선정 확인:** 경계값, 먼저 실행되는 분기, fall-through와 예외를 몇 개의 직접 추적 예로 확인해야 합니다.

## 5. 환경설정 대조

- **쓸 장면:** 개발/검증/운영 설정 파일에서 의도치 않게 달라진 키를 확인합니다.
- **스킬의 추가 가치:** 공백과 줄 순서보다 설정 경로를 기준으로 비교하고, 누락/값 차이/변수 미해결을 나눕니다. 비밀번호는 값 대신 동일 여부만 출력합니다.
- **입력 부담:** 두 설정 파일 또는 명시된 두 폴더로 시작합니다. 여러 프로필 중 비교 대상이 모호할 때만 선택합니다.
- **출력:** `키 경로 | 개발 | 운영 | 확인할 점` 표. 파일 차이와 런타임에 최종 적용된 값은 구분합니다.
- **기존과 차이:** 오류 원인 추측이나 전체 QA가 아니라, 실행 전에도 가능한 환경별 설정 대조입니다.
- **원문:** Homeport의 [dyff](https://github.com/homeport/dyff). **외부 SKILL이 아닌 설정 비교 도구**에서 출력 방식과 경로 기반 대조를 참고하는 자체 설계 후보입니다.
- **반입 시 수정:** dyff 설치를 필수로 하지 않습니다. 지원 범위를 JSON과 단순 properties부터 시작하고, YAML/XML의 병합/중복/네임스페이스를 지원하지 못하면 그 사실을 표시합니다. 미해결 환경변수를 추측하지 않습니다.
- **선정 확인:** 키 순서만 바뀐 경우와 값이 바뀐 경우를 구분하고, 중복 키를 버리거나 비밀값을 노출하지 않아야 합니다.

## 6. 문서와 구현 대조

- **쓸 장면:** 오래된 설명서의 파라미터, 설정값, 화면 동작이 현재 구현과 맞는지 확인합니다.
- **스킬의 추가 가치:** 문장의 주장과 구현 근거를 연결하고, 불일치 부분의 교체 문장을 제공합니다.
- **입력 부담:** 문서와 관련 코드가 같은 작업 범위에 있으면 스스로 짝을 찾습니다. 이름만 비슷한 파일을 근거로 삼지 않습니다.
- **출력:** `문서 위치 | 현재 설명 | 구현 근거 | 수정 제안` 표와 요청 시 수정본.
- **기존과 차이:** 보고서 생성이나 project-playbook의 규칙 저장과 달리, 기존 설명의 사실 관계를 점검합니다.
- **원문:** Microsoft의 [hve-core documentation](https://github.com/microsoft/hve-core/blob/main/.github/skills/hve-core/documentation/SKILL.md)와 [code-doc-mapping](https://github.com/microsoft/hve-core/blob/main/.github/skills/hve-core/documentation/references/code-doc-mapping.md).
- **반입 시 수정:** 원본 저장소 전용 경로 매핑과 CI 전제를 제거합니다. 코드가 항상 정답이라고 가정하지 않고, 문서가 요구사항이라면 구현 불일치로 보고합니다. 읽을 수 없는 HWP/PDF/XLSX를 읽었다고 하지 않습니다.
- **선정 확인:** 의도적으로 바꾼 설정 기본값/필수 필드를 찾아내고, 일치하는 문장을 불필요하게 고치지 않아야 합니다.

## 7. 숫자 변동 분해

- **쓸 장면:** 전월 대비 합계, 계획 대비 실적, 배치 전후 집계가 달라진 부분을 설명합니다.
- **스킬의 추가 가치:** 전체 증감이 어떤 항목의 증가/감소로 구성됐는지 합계가 맞는 기여도 표를 만듭니다.
- **입력 부담:** 비교할 표 두 개가 있으면 항목과 단위를 확인합니다. 원본 데이터에 없는 원인을 이야기로 채우지 않습니다.
- **출력:** `기준 합계 + 항목별 증감 = 비교 합계` 표. 워터폴 차트는 도움이 될 때만 추가합니다.
- **기존과 차이:** 1번이 개별 행의 불일치를 찾는다면, 이 후보는 집계값 변화의 구성을 풉니다. visual-brief는 이미 확인된 내용을 요약합니다.
- **원문:** Anthropic 공식 [variance-analysis](https://github.com/anthropics/knowledge-work-plugins/blob/main/finance/skills/variance-analysis/SKILL.md).
- **반입 시 수정:** 회계 전용 명칭을 일반 지표로 확장하되, 가산 가능한 값만 합산합니다. 비율/평균은 가중치와 분모를 확인하고, 수학적 기여도와 실제 업무 원인을 구분합니다. 원문 예시의 복합 분해식도 그대로 신뢰하지 않고 잔차까지 검산해야 합니다.
- **선정 확인:** 시작값+증감=끝값이 일치하고, 분모 0이나 비교 기간 차이를 숨기지 않아야 합니다.

## 8. 현업 확인표

- **쓸 장면:** 개발 완료 후 담당자에게 무엇을 어떤 순서로 확인해달라고 할지 정리합니다.
- **스킬의 추가 가치:** 현재 요구사항을 사람이 따라 할 조작 순서와 눈으로 판단 가능한 기대 결과로 바꿉니다.
- **입력 부담:** 현재 기능의 요구사항/화면 코드/사용 가능한 캡처를 읽고 핵심 업무 흐름부터 뽑습니다.
- **출력:** `준비 조건 | 조작 순서 | 기대 결과 | 실제 결과 | 판정`의 짧은 `acceptance.csv` 또는 Markdown.
- **기존과 차이:** qa-sweep의 에이전트 실행 검증과 달리 현업에게 전달할 미실행 검수표를 만듭니다. 프로젝트 온보딩 가이드와도 대상이 다릅니다.
- **원문:** Nao의 [manual-testing](https://github.com/naodeng/awesome-qa-skills/tree/main/skills/en/testing-types/manual-testing)와 [실행 지침](https://github.com/naodeng/awesome-qa-skills/blob/main/skills/en/testing-types/manual-testing/prompts/manual-testing.md).
- **반입 시 수정:** 장문 계획서를 만들지 않고 핵심 사례부터 제공합니다. 화면에서 보이지 않는 내부 구현을 현업 판정 기준으로 요구하지 않습니다.
- **선정 확인:** 구현을 모르는 동료가 표만 보고 실제 조작과 판정을 할 수 있어야 합니다. 판정 칸은 미실행 상태로 둡니다.

## 9. 조건 조합 압축

- **쓸 장면:** 권한×상태×처리 유형×입력 조건 등 조합이 많아 전부 시험하기 어려울 때 사용합니다.
- **스킬의 추가 가치:** 유효한 두 조건 값의 조합을 포함하는 테스트 집합을 만들고, 어떤 쌍이 포함/제외/미확인인지 검산합니다.
- **입력 부담:** enum과 명시된 조건에서 요인/값을 추출합니다. 허용 조합이 불명확하면 임의로 유효하다고 정하지 않습니다.
- **출력:** `combinations.csv`와 `검증된 조건 쌍/전체 유효 조건 쌍` 요약. 위험한 3개 이상 조건의 결합은 별도 필수 케이스로 추가합니다.
- **기존과 차이:** 2번의 구체적인 값 생성과 달리, 어떤 조건들을 함께 시험할지 선택합니다. parallel-batch처럼 작업자를 나누는 기능은 없습니다.
- **원문:** Nao의 [pairwise-testing](https://github.com/naodeng/awesome-qa-skills/tree/main/skills/en/testing-types/pairwise-testing)와 [실행 지침](https://github.com/naodeng/awesome-qa-skills/blob/main/skills/en/testing-types/pairwise-testing/prompts/pairwise-testing.md).
- **반입 시 수정:** 원문은 분석/권고 중심입니다. 실행 가능한 조합표까지 제공하려면 생성기와 독립 커버리지 계산을 추가 구현해야 합니다. 브라우저 내 JavaScript 등 이미 가능한 로컬 실행으로 구성하고 의존 패키지 설치를 요구하지 않습니다.
- **선정 확인:** 각 유효 조건 쌍이 실제 포함됐는지 기계적으로 검사해야 합니다. 최소 케이스 수, 모든 조합 검증, 결함 없음은 보장하지 않습니다.

## 10. 로그와 샘플 가명처리

- **쓸 장면:** 동료나 다른 팀에 넘길 로그/요청 샘플에서 식별정보를 가리되 데이터 간 대응 관계는 남깁니다.
- **스킬의 추가 가치:** 같은 식별값을 같은 토큰으로 바꿔 요청-응답과 반복 로그를 따라갈 수 있게 합니다. 처리 내역과 남은 의심 항목을 제공합니다.
- **입력 부담:** 지정 파일/선택 필드와 문맥에서 식별정보 후보를 찾습니다. 메타 이름만으로 고객번호라고 단정하지 않습니다.
- **출력:** 가명처리한 사본 + 항목별 건수. 원문은 보존하고 복원 매핑은 공유본에 포함하지 않습니다.
- **기존과 차이:** task-to-tool이 이미 끝난 작업의 도구화를 다룬다면, 이 후보는 가명처리의 일관성과 잔존 정보 확인 절차를 갖춥니다. 2번의 완전 합성 데이터 생성과도 구분합니다.
- **원문:** 커뮤니티 프로젝트 [Redacta](https://github.com/nickjlamb/redacta), [SKILL.md](https://github.com/nickjlamb/redacta/blob/main/SKILL.md).
- **반입 시 수정:** 원본은 영미권 의료 식별자와 Python을 사용합니다. 한국어 업무 문맥과 명시된 필드에 맞춰 새 처리 규칙이 필요합니다. 스캔 PDF와 이미지까지 처리한다고 하지 않으며 완전 익명화/반출 승인 도구로 표시하지 않습니다.
- **선정 확인:** 같은 값은 같은 토큰, 다른 값은 다른 토큰으로 남고 원문/토큰 충돌을 처리해야 합니다. 검출 누락을 측정할 샘플이 없으면 식별정보 제거 완료를 보장하지 않습니다.

## 선정에서 제외한 방향

- 병렬 개발 지휘, 자동 계획 실행, 세션 기억, 스킬 자동 생성: 기존 후보와 중복하거나 이번 사용 피드백과 맞지 않습니다.
- Git/PR/CI 중심 자동화, 브라우저 자동화 도구가 반드시 필요한 작업: 사내 공통 환경으로 보기 어렵습니다.
- 일반 오류 해설, 리팩터링 탐색, API 명세 생성, 보고서와 흐름도 생성: 앞서 공유한 사내 스킬 및 기존 Worklens와 겹칩니다.
- 긴 인터뷰로 시작하는 기획 스킬: 짧은 요청을 선호하는 실제 사용자에게 입력 부담이 큽니다.
- 공급업체의 클라우드 연결을 핵심으로 하는 인기 스킬: 폐쇄망에 그대로 옮기기 어렵습니다.

## 출처를 어떻게 평가했나요?

공식 조직 원문: Anthropic, Microsoft. GitHub의 awesome-copilot은 GitHub 조직이 운영하는 **커뮤니티 기여 모음**입니다.
개인/커뮤니티 원문: Impeccable, Nao, Forge, Redacta. dyff는 스킬이 아니라 설계 참고 도구입니다.
목록 사이트는 발견에만 활용하고, 최종 선정은 원 저장소의 지침과 필요한 도구를 읽고 판단했습니다.

현재 공개 원문을 확인했다는 사실이 인기 순위, 시간 절감률, 외부 전문가의 이번 후보 검수, 사내 Qwen 호환성을 입증하지는 않습니다.
상위 1~3번은 결과가 바로 눈에 보이고 재사용할 파일이 남는다는 이유로 먼저 추천합니다.

## 사내 적용 후 확인할 기준

1. 실제 업무의 작은 파일과 짧은 요청으로 시작해 사용자의 재설명을 얼마나 요구하는지 봅니다.
2. 같은 입력을 일반 에이전트와 스킬에 각각 주고 결과 정확성, 재질문, 수작업 수정량을 비교합니다.
3. 데이터 계산/조합 생성은 가능하면 결정적 코드로 검사합니다. SKILL.md 구조 검사만으로 동작 검증을 대신하지 않습니다.
4. 일반 에이전트와 차이가 없는 후보는 추가하지 않거나 기존 스킬의 작은 기능으로 합칩니다.
5. 스킬 확정 시 지침은 영어, 질문과 결과는 한국어로 작성합니다. 외부 원문을 포함한다면 버전, 라이선스, 고지와 변경 내역을 함께 관리합니다.
