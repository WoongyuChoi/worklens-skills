먼저 API 인증·권한 검증, 개인정보 로그 노출 점검, 입력 경로 보안 검토, 라이브러리 취약점 영향 판정을 우선 사용합니다. 에이전트 입력 경계 검증은 실제 호스트 trace를 볼 수 있을 때 선택합니다. 다섯 개 모두 짧은 요청에서 소스와 기존 자료를 찾아 시작하며, 결과 HTML은 공통 산출물로 제공합니다.

사용자가 제시한 문제는 “무인증 API에서 개인정보가 보임 → 소스에서 원인 확인 → 전체 API 점검 범위를 관리 → 수정과 발표에 사용할 근거”입니다. 이에 따라 검사 횟수보다 정상 대조군, 허용·거부 기대값, 실제 데이터/효과 관측, 미검증 범위를 중시합니다. 내부 위치에서 접속된 것만으로 인터넷 외부 노출을 판정하지 않습니다.

추가 캡처 반영 — 개인정보 로그 노출

사용자가 추가한 2026-10-14 점검 사례는 불필요한 개인정보 출력 제외와 기존 로그 정책 재검토를 요청합니다. 실제 로그는 개인정보 때문에 제공할 수 없고, 서비스별 컬럼명 목록을 활용하는 방식입니다. 해당 원본 로그·내부 서버 경로·시스템명은 이 저장소에 수집하거나 복제하지 않습니다.

이에 따라 privacy-log-audit를 다섯 번째 항목으로 추가하되 현장 우선순위는 두 번째로 높였습니다. log.info("{}", dto), Lombok/수동 toString, JSON 직렬화, 예외 메시지, HTTP body/header 기록, SQL bind trace, MDC와 telemetry 속성을 따라갑니다. 단순 주민번호·전화번호 정규식 탐지나 데이터 마스킹에 그치지 않고 왜 이 필드가 기록되는지와 어떤 출력 경로를 줄일지를 결정합니다.

OpenTelemetry의 민감 데이터 공식 지침은 업무별 민감도를 도구가 자동 판단할 수 없으며 관측 목적에 필요한 정보만 수집하도록 설명합니다. 2026-05-19 레거시 환경 보안 글도 전체 payload 수집을 줄이고 목적 있는 속성을 선택하는 접근을 다룹니다. 여기서는 OpenTelemetry 설치를 요구하지 않고 기존 logger에 적용할 판단 기준으로 사용합니다. OWASP Logging 지침은 보안 사건 추적에 필요한 이벤트를 유지하면서 토큰·민감 개인정보 등의 직접 기록을 피하는 기준입니다. 이 문서들은 새 사건으로 소개하지 않고 현재 구현의 기준으로 사용합니다.

새 스킬은 불필요한 필드를 먼저 출력 대상에서 제외하고, 장애 분석에 반드시 필요한 상관관계는 승인된 trace ID·오류 코드 등의 최소 정보로 유지합니다. 로그 레벨만 낮추거나 수집 서버에서 뒤늦게 가리는 조치가 최초 파일 출력을 제거했다고 간주하지 않습니다. 실제 로그를 검사해도 보고서에는 값·원문·원문 hash를 싣지 않고 필드명·위치·개수·확인 수준만 남깁니다.

GitHub의 2026-08-06 공급망 글은 악성 패키지 권고를 Maven·PyPI 등 8개 생태계로 확장하면서 출처·철회·중복·생태계 표현 차이를 다룹니다. 설치/빌드에서 실행되는 악성 패키지 위험은 런타임 호출이 없다는 이유만으로 제외하지 않게 했습니다.

실제 반입 절차는 다음과 같습니다.

  1. 외부 조사에서 공식 공지의 URL·공개일·수정일·조회일·범위·필수 조건·수정 버전 경로를 확보합니다.
  2. 회사 반입 절차에 맞춰 snapshot을 가져옵니다. 출처 원문을 별도 보관했다면 실제 바이트의 hash를 기록하고, 보관하지 않았다면 hash를 꾸며내지 않습니다.

  4. 새로운 snapshot의 수정·철회·별칭 변경을 기존 판정과 대조하고, 달라진 항목만 재검토합니다.

6. 사용과 검증의 현실적인 경계

  • 스킬은 사내 Agent의 현재 파일·셸·HTTP 기능을 활용하는 절차와 보조도구입니다. 호스트에 없는 도구를 추가하지 않습니다.
  • 실제 API runner는 지정 origin·경로·GET/HEAD의 읽기 사례만 자동 수행합니다. POST/PATCH/DELETE와 부작용 있는 GET은 별도 테스트 환경·데이터·복구 조건을 가진 계획으로 남깁니다.
  • endpoint 분모, 실행한 사례, 미실행 이유를 남깁니다. 정적 목록에 없는 동적 route나 외부 서비스까지 “전수 점검 완료”로 표시하지 않습니다.
  • 결과에 credential·cookie·실제 응답 원문을 저장하지 않습니다. API runner는 합성 마커와 필요한 판정 값만 사용합니다.
  • HTML에는 inline CSS/JavaScript와 SVG를 사용합니다. 서버 연결·CDN·외부 폰트가 필요하지 않습니다.
  • 로컬 테스트와 실제 사내 Qwen 동작은 별도입니다. 구체적인 실행 결과·한계는 검증 기록 (팩의 VALIDATION.md)을 참조하세요.

첫 현장 적용은 전체 서비스보다 읽기 API가 있는 작은 모듈 한 개가 적합합니다. Agent가 소스에서 API 목록과 후보를 만들고, 정상 계정·다른 테스트 주체의 대조 결과를 남긴 뒤, 개발자가 실제 수정할 문제와 남은 질문이 나오는지 확인하면 다섯 스킬의 효용을 빠르게 판단할 수 있습니다.

7. 구현 결과와 실제 확인한 수준

다섯 스킬에는 SKILL 지침, 참조 문서, 합성 예제, 선택 실행 도구와 동일 형식의 독립 HTML 보고서를 넣었습니다. Node 표준 모듈만 사용하며 추가 패키지는 설치하지 않았습니다. 각 폴더만 복사해 사용할 수 있습니다.
